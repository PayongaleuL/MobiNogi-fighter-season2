## 1. Executive Summary

본 프로젝트는 **React 19 + Vite 8 기반의 정적 웹 계산기**이며, 룬·보석·인장·스킬·전투 기믹을 조합하여 DPS를 산출합니다. `Vitest 4`와 `Playwright`는 개발 의존성에 포함되어 있지만, 공식 테스트 스크립트와 커버리지 설정은 아직 정의되어 있지 않습니다. 현재 정적 분석은 Oxlint의 React 관련 두 규칙에 한정되고, 배포 워크플로는 `npm ci`와 빌드 성공만 확인한 뒤 GitHub Pages에 배포합니다. [2] [5]

현재 커밋을 기준으로 수행한 **읽기 전용 기준선 검증**에서는 빌드와 13개 단위 테스트가 통과했습니다. 린트는 오류 없이 종료했으나 경고 26개를 출력했습니다. 임시 커버리지 어댑터로 유틸리티 테스트만 측정한 결과는 Statements **75.26%**, Branches **60.44%**, Functions **77.77%**, Lines **81.68%**였습니다. 이 수치는 컴포넌트가 측정 대상에 포함되지 않은 결과이므로, 전체 애플리케이션 커버리지로 해석해서는 안 됩니다. Vitest는 기본적으로 테스트 중 import된 파일만 보고하기 때문에, 향후 `src/**/*.{js,jsx}`를 명시적으로 포함해야 미실행 컴포넌트도 누락 없이 측정됩니다. [6] [7]

## 2. Identified Risk Areas

### 2.1 테스트 경계와 모킹 방침

현재 애플리케이션에는 DB 트랜잭션이나 외부 네트워크 연동이 없으므로, 존재하지 않는 DB·HTTP 모킹을 만들지 않습니다. 순수 유틸리티는 실제 함수와 고정 fixture를 사용해 검증합니다. UI 단위 테스트에서는 결정성을 위해 `localStorage`, `window.confirm`, `window.prompt`, `console.error`, Clipboard API만 격리합니다. `calculateDPS`는 `Calculator`의 저장·상태 전달만 확인하는 컴포넌트 테스트에서만 대체하고, 최종 통합 및 E2E에서는 실제 엔진을 사용합니다.

향후 API 또는 서버 DB가 추가되면, 이 계획에 **계약 테스트 및 격리 환경**을 추가합니다. HTTP는 MSW 기반 요청 모킹과 성공·타임아웃·4xx/5xx·잘못된 응답 스키마 테스트를, DB는 마이그레이션된 임시 DB에서 트랜잭션 원자성·롤백·동시성 테스트를 수행합니다. SQL은 문자열 연결을 금지하고 파라미터 바인딩 테스트를 필수화합니다.

| `parseSkillMarkdown` | 패시브·능동 스킬·스탠스·쿨다운 해석 | 빈 문서, 잘린 섹션, 중복 스킬, 잘못된 숫자, 형식 변형, 미지 스탠스 | 실패가 침묵 데이터 훼손으로 이어지지 않고, fallback 또는 명시 오류 정책이 지켜집니다. |
| `parseRuneMarkdown` | 헤더·정제 문장·정규식 스탯·조건부 밤의 축복 | 빈·공백 문서, 헤더 누락, 소수점, 다중 수치, 문장 순서 변경, OCR 노이즈, 미지 텍스트·카테고리 | 실제 마스터 문서의 룬 수·이름·type·대표 스탯이 승인된 골든 fixture와 일치하고, malformed 입력은 안전하게 무시 또는 실패합니다. |

`calculateDPS`에는 추가로 **속성 기반 테스트(property-based testing)**를 도입합니다. 유효 범위 내의 입력 조합을 반복 생성하여 결과가 `NaN` 또는 `Infinity`가 되지 않고, 사이클 시간이 양수이며, 확률 클램프가 지켜지는지를 확인합니다. 공식의 단조성이 명확한 경우에만 “공격력 증가 시 총 공격력이 감소하지 않음” 같은 불변식을 사용합니다. 실제 게임 공식이 비선형 또는 캡 구조라면 단조성 가정을 강제하지 않고, 승인된 기준표를 우선합니다.

### 3.2 기준 데이터 및 회귀 테스트 전략

수식·룬·스킬 데이터에는 **골든 테스트**를 사용합니다. 기준값은 기존 엑셀 공식 또는 제품 책임자가 승인한 계산 결과에서 추출하며, 각 fixture에는 출처·입력·기대 결과·허용 오차를 기록합니다. 실데이터 파일을 그대로 읽는 테스트만으로는 데이터와 기대값이 함께 잘못 바뀌는 회귀를 놓칠 수 있으므로, 최소한 다음 네 종류를 고정합니다.

| 골든 fixture | 대표 시나리오 | 검증 목적 |
| --- | --- | --- |
| 기본 전투 | 룬·보석·인장 없음, 기본 보스·기본 딜사이클 | 엔진의 기준선과 fallback 데이터 검증 |
| 고강화 조합 | 모든 룬 슬롯, 초월, 보석, 인장, 시즌 패시브 활성 | 누적 계수·반올림·우선순위 검증 |
| 보스별 조합 | 모든 지원 보스와 무방비/궁극 시간 비중 | 방어·치명타 저항·시간 가중치 분기 검증 |
| 파서 데이터 | 실제 Markdown 및 의도적으로 변형한 문서 | 데이터 변환의 스키마·회귀·실패 처리 검증 |

### 3.3 React 컴포넌트 및 통합 테스트

컴포넌트 테스트에는 `jsdom`, React Testing Library, user-event를 추가하고, 사용자 관점의 역할·레이블·표시 결과로 단언합니다. 내부 state를 직접 검사하지 않으며, 화면 입력 → 저장/복원 → DPS 표시 변화의 경로를 검증합니다.

| 흐름 | 통합 테스트 시나리오 | 판정 기준 |
| --- | --- | --- |
| 초기화·파서 fallback | 룬 Markdown 파싱 성공/실패와 `runes.json` fallback | 파싱 실패가 빈 화면이나 예외를 만들지 않고, 계산 가능한 기본 상태가 렌더링됩니다. |
| 저장소 복원 | 현재·구버전 키, malformed JSON, 부분 객체, 저장소 쓰기 실패 | 유효 데이터만 복원되고, 손상 데이터는 안전한 기본값으로 돌아가며 사용자 조작이 계속 가능합니다. |
| 룬 장착·초월 | 올바른 타입 장착, 다른 타입 거부, 장착 해제 후 초월 초기화, 편집 룬 반영 | 선택 상태·초월 상태·최종 DPS 입력이 일관됩니다. |
| 프리셋 | 저장, 덮어쓰기, 삭제, 취소, 새로고침 후 복원, 로드 | 제품 계약상 프리셋에 포함돼야 하는 모든 상태가 빠짐없이 복원됩니다. `seals`·`gimmicks` 포함 여부는 구현 전 승인합니다. |
| 리셋 | 확인/취소, 모든 관련 상태 초기화, 자동 저장 재생성 | “모든 설정 초기화”라는 UI 문구와 실제 초기화 범위가 일치합니다. |
| 보석 UI | 옵션 최대 3개, 특수 보석 선택 제한, 합계 표시 | UI 합계가 `calculateGemStats`와 동일하며 잘못된 조합을 허용하지 않습니다. |
| 입력 유효성 | 빈 값, 문자열, 음수, 소수, 최대값 초과 | 오류 표시·정규화·차단 중 선택한 계약이 일관되며 계산 결과가 유한 수입니다. |
| XSS 회귀 | 룬 이름·프리셋 이름에 HTML 형태 문자열 입력 | 문자열은 텍스트로 렌더링되고 스크립트 실행·DOM 삽입·페이지 오류가 없습니다. |

### 3.4 E2E 테스트 전략

E2E는 Playwright로 실제 production build를 미리보기 서버에서 열어 수행합니다. 각 시나리오는 데스크톱과 모바일 뷰포트를 모두 확인하고, 완료 시 콘솔 오류·unhandled page error·빈 화면이 없어야 합니다. E2E는 데이터 세부 수식 전체를 재검증하는 용도가 아니라, 독립적으로 통과한 단위·통합 테스트가 실제 번들에서 연결되는지를 검증합니다.

| 우선순위 | 핵심 사용자 시나리오 | 검증 결과 |
| --- | --- | --- |
| P0 | 첫 접속 후 기본 DPS 확인 → 수치 변경 → 결과 갱신 | 결과가 렌더링되고 의도된 변경에 따라 재계산됩니다. |
| P0 | 룬 장착·초월·가동률·스탠스 선택 | 호환 규칙이 지켜지고 결과가 정상 표시됩니다. |
| P0 | 보석 3옵션 구성과 특수 보석 선택 | 제한 조건과 요약 수치가 유지됩니다. |
| P0 | 프리셋 저장 → 페이지 새로고침 → 프리셋 로드 | 승인된 전체 상태가 복구됩니다. |
| P1 | 구버전 자동 저장 데이터 마이그레이션 | 데이터 손실·페이지 오류 없이 최신 형식으로 전환됩니다. |
| P1 | 테마 전환 및 모바일 390px 수준 화면 | 테마가 새로고침 후 유지되고 주요 조작이 접근·사용 가능합니다. |
| P1 | 변경된 의존성/아이콘 포함 production build | 루트 렌더링 실패 및 화면 전체 백색 회귀를 탐지합니다. |

### 3.5 커버리지 목표 및 적용 순서

커버리지 수치는 **품질 신호**이지 결함 부재의 증명이 아닙니다. 따라서 먼저 테스트 대상을 명시하고, 핵심 분기와 실제 사용자 시나리오를 채운 후 차단 임계값을 적용합니다. V8 커버리지 제공자는 Vitest의 권장 선택지이며, `@vitest/coverage-v8` 패키지와 include/exclude·threshold 설정으로 실행할 수 있습니다. [6] [7]

| 범위 | 현재 관측치 | 도입 후 목표 | 게이트 적용 조건 |
| --- | --- | --- | --- |
| 측정 대상 핵심 유틸리티 | Statements 75.26%, Branches 60.44%, Functions 77.77%, Lines 81.68% | Statements·Branches·Functions·Lines 모두 **95% 이상** | 룬 파서·계산기·보석·인장 경계 테스트를 추가하고, 전역 95% 임계값으로 차단합니다. |
| `calculator.js` | Branches 57.58% | Lines/Statements/Functions/Branches 모두 **95% 이상** | 골든 fixture와 보스·스탠스·0값·오류 입력 테스트 완료 후 적용합니다. |
| 파서 모듈 | 룬 파서 미측정, 스킬 파서 Branches 93.24% | Lines/Statements/Functions/Branches 모두 **95% 이상** | malformed·실데이터·fallback 테스트를 포함해야 합니다. |
| 전체 `src` | 산출 불가 — 컴포넌트 미포함 | 별도 UI 통합·E2E 회귀 테스트 100% 통과 | UI는 렌더링 행 수로 품질을 판단하지 않고, 핵심 사용자 시나리오와 페이지 오류 0건을 병행 검증합니다. |

제외 대상은 CSS, 정적 이미지, 생성 산출물, 진입점에서만 수행되는 부트스트랩 코드처럼 실행 책임이 없는 파일로 한정합니다. 테스트하기 어렵다는 이유로 비즈니스 로직을 제외하거나, coverage ignore 주석을 추가하는 경우에는 PR 설명과 코드 리뷰 승인을 필수로 합니다. CI에는 텍스트 요약, lcov, HTML 보고서를 산출물로 보존합니다.

### 3.6 정적 분석·보안 분석 계획

정적 분석은 빠른 피드백을, 보안 분석은 배포 전 차단과 추적성을 담당합니다. 현재 Oxlint 설정은 Hooks 오류와 컴포넌트 export 경고만 활성화하므로, lint 성공만으로 입력 오류·접근성·위험한 DOM 사용을 충분히 확인할 수 없습니다. [2]

| 분야 | 도구·규칙 계획 | 차단 기준 | 초기 조치 |
| --- | --- | --- | --- |
| 코드 품질 | Oxlint 규칙을 확장하고 React Hooks, 미사용 변수·import, 의심스러운 조건문, `console` 정책, JSX 접근성 규칙을 적용합니다. | 오류 0개, 기준선 정리 완료 후 경고 0개 | 기존 26개 경고를 먼저 분류·수정 또는 승인된 예외로 문서화합니다. |
| 포맷 일관성 | Prettier 또는 기존 팀 포맷터를 단일 기준으로 선택하고 check 모드를 CI에 추가합니다. | 포맷 불일치 0개 | 자동 수정은 개발자 로컬 작업으로만 제공하고 CI는 검사만 수행합니다. |
| JavaScript SAST | Semgrep JavaScript 규칙과 프로젝트 고유 규칙으로 `eval`, `innerHTML`, `dangerouslySetInnerHTML`, 안전하지 않은 URL/DOM API를 검사합니다. | High/Critical 및 승인되지 않은 Error 등급 0개 | 외부 규칙을 사용할 경우 메트릭 전송을 비활성화하고, CI는 `--error`로 종료 코드를 반영합니다. Semgrep은 CI용 실패 종료 코드와 로컬 스캔을 구분해 지원합니다. [9] |
| 시크릿 탐지 | Gitleaks 또는 동등 도구로 현재 트리와 Git 이력을 검사합니다. | 실제 시크릿 0개 | 예제 값은 허용 목록을 최소화하고 만료 사유를 기록합니다. |
| 의존성 감사 | `npm audit`를 lockfile 기준으로 실행하고 Dependabot 또는 동등한 업데이트 알림을 활성화합니다. | 런타임 High/Critical 0개; 개발 의존성 High는 수정 기한 내 0개 | 현재 전체 개발 트리의 High 2건부터 원인 버전·호환성·lockfile 갱신 여부를 검토합니다. |
| 저장 데이터 안전성 | `localStorage` JSON의 버전·스키마·범위를 검증하고 예상치 못한 키를 제거 또는 무시합니다. | 손상 상태가 계산·렌더링 오류를 만들지 않음 | 이는 보안 경계라기보다 사용자 변경·오래된 데이터로 인한 무결성/가용성 위험 완화입니다. |

현재 DB와 서버 API가 없으므로 SQL Injection과 서버 측 인증·인가 테스트는 **해당 대상이 추가될 때까지 적용 제외**입니다. 다만 사용자 입력이 UI에 표시되고 브라우저 저장소에 남으므로, DOM 기반 XSS 및 상태 오염 회귀 테스트는 지금부터 적용합니다.

### 3.7 품질 관문(Quality Gate) 정의

GitHub Actions는 Node 프로젝트에서 동일한 설치·빌드·테스트 명령을 CI 단계로 실행하도록 안내합니다. 배포는 검증이 성공한 후에만 연결해야 합니다. [8]

| 순서 | 품질 관문 | PR 기준 | `main` 배포 기준 | 실패 시 조치 |
| --- | --- | --- | --- | --- |
| 1 | 잠금 의존성 설치 | `npm ci` 성공 | 동일 | lockfile과 manifest 불일치 또는 설치 실패를 수정합니다. |
| 2 | 포맷·린트 | 오류 0개, 경고 0개 | 동일 | 규칙 위반을 수정하거나 승인된 예외를 최소 범위로 기록합니다. |
| 3 | 단위·컴포넌트 테스트 | 전체 통과 | 동일 | 실패한 기능은 회귀로 분류하고 수정 전 병합을 차단합니다. |
| 4 | 커버리지 | 단계별 임계값 충족 | 동일 | 테스트를 추가하거나 계약상 불필요한 코드를 제거/분리합니다. 임의 제외는 금지합니다. |
| 5 | production build | 성공 | 성공 | 번들·import·환경 차이를 해결합니다. |
| 6 | Playwright 핵심 E2E | P0 시나리오 100% 통과 | 동일 | 스크린샷·trace를 산출물로 저장하고 페이지 오류를 수정합니다. |
| 7 | SAST·시크릿·의존성 감사 | 신규 High/Critical 0개 | High/Critical 0개 | 오탐은 근거를 남겨 최소 범위로 억제하고, 실제 이슈는 수정 또는 배포 차단합니다. |
| 8 | 배포 승인 | 해당 없음 | 1–7 전부 성공 후만 실행 | 검증 실패 시 Pages artifact 생성·배포를 수행하지 않습니다. |

### 3.8 CI/CD 검증 자동화 선택지

이 프로젝트의 자동 검증은 기존 GitHub Actions의 push/PR 이벤트에 결합하는 결정적 작업입니다. 아래 두 선택지는 모두 실행 가능하며, **옵션 A가 더 가볍고 옵션 B가 더 강한 통제력**을 제공합니다. 적용 전 저장소 관리 방식과 유지 비용을 고려해 하나를 선택합니다.

| 접근 방식 | 구성 및 트레이드오프 | 비용 | 설정 복잡도 |
| --- | --- | --- | --- |
| **옵션 A — 단일 워크플로 확장** | 현재 배포 워크플로에 lint → test → coverage → build → P0 E2E → 배포 순서를 추가합니다. 설정 파일은 적지만 PR 검증과 배포 책임이 한 파일에 모입니다. | 기존 CI 사용 범위 내 | 낮음 |
| **옵션 B — 검증/배포 분리 및 브랜치 보호** | PR·push에서 독립된 `verify` 검증을 실행하고, 배포 워크플로는 `verify` 성공 후 `main`에서만 실행합니다. 필수 상태 검사·보안 감사·보고서 보존을 설정할 수 있어 통제력은 높지만 운영 설정이 추가됩니다. | 기존 CI 사용 범위 내 | 중간 |

두 옵션 모두 테스트·커버리지·보안 검사 결과와 Playwright 실패 산출물을 보존해야 합니다. 릴리스 책임자와 협업자가 분리되어 있거나 PR 병합 통제가 필요한 경우 옵션 B가 더 적합하며, 개인 프로젝트에서 빠르게 최소 관문부터 적용하려면 옵션 A가 더 가볍습니다. 이 문서는 특정 옵션을 사전 선택하지 않습니다.

## 4. Step-by-Step Implementation Checklist

아래 체크리스트는 **승인 후 구현 순서**입니다. 각 단계는 선행 단계의 산출물과 통과 기준을 만족한 경우에만 다음 단계로 진행합니다. 테스트가 없는 상태에서 커버리지 기준만 먼저 강제하여 정상 개발을 막지 않도록, 측정 → 보강 → 차단의 순서를 지킵니다.

### 4.1 1단계 — 환경 설정 및 기준선 고정

- [ ] `package.json`에 표준 명령을 정의합니다: 개발용 watch test, 일회성 test, coverage, lint, format check, E2E, 전체 verify.

- [ ] Vitest 설정을 추가하고 V8 커버리지 제공자, `src/**/*.{js,jsx}` 대상, 명시적 제외 목록, 텍스트·lcov·HTML 보고서를 설정합니다. 공식적으로 제공되는 coverage provider와 threshold 설정을 사용합니다. [6] [7]

- [ ] React Testing Library, user-event, jsdom 및 테스트 setup 파일을 추가합니다. `localStorage`, confirm/prompt, console, Clipboard API의 공통 mock·복원 규칙을 정의합니다.

- [ ] Playwright 설정을 추가하고 production build 미리보기 서버를 테스트 시작 조건으로 설정합니다. 데스크톱·모바일 프로젝트, trace·screenshot 보존 정책을 정의합니다.

- [ ] Oxlint 경고 26개를 원인별로 분류하여 수정하고, 경고 0개 정책으로 전환할 준비를 합니다.

- [ ] 현재 전체 개발 의존성 감사의 High 2건을 재현·분석하여, 호환 가능한 버전 갱신과 lockfile 검증 계획을 확정합니다.

- [ ] 이 단계의 기준선 결과(테스트 수, 커버리지, lint, audit, build 시간)를 `results/quality-baseline` 또는 동등한 비배포 경로에 기록합니다.

**완료 조건:** 모든 개발자가 동일한 명령으로 테스트·커버리지·빌드를 재현할 수 있고, 아직 차단 임계값은 적용하지 않습니다.

### 4.2 2단계 — 최우선 코어 로직 단위 테스트

- [ ] `calculator.js`의 룬·초월·인장·보석·보스·스탠스·시즌 패시브·가중 평균을 독립 fixture로 분할합니다.

- [ ] 개조 레벨의 전 구간 경계와 0/누락/범위 외 입력에 대한 계약을 테스트로 고정합니다.

- [ ] DPS 반환 객체의 모든 수치가 유한 수인지, 시간·확률 처리와 반올림이 계약에 맞는지 검증합니다.

- [ ] 실제 승인 수식에서 추출한 기본·고강화·보스별 골든 fixture를 추가하고 절대값/허용 오차로 단언합니다.

- [ ] `sealCalculator`와 `gemCalculator`의 전체 슬롯·옵션·등급·누락 값·알 수 없는 값 테스트를 추가합니다.

- [ ] 속성 기반 테스트로 유효 입력 공간의 `NaN`/Infinity/0 나눗셈 회귀를 탐지합니다.

- [ ] 계산기·인장·보석 모듈의 개별 커버리지 목표를 달성한 후, 해당 파일에 대한 per-file threshold를 활성화합니다.

**완료 조건:** 핵심 유틸리티의 기준값·경계·오류 정책이 테스트로 고정되고, 계산기 Branch 85% 이상 및 기타 핵심 유틸리티 Branch 80% 이상을 달성합니다.

### 4.3 3단계 — 파서·상태 통합·E2E 보강

- [ ] `parseRuneMarkdown` 전용 테스트 파일과 실제 Markdown 기반 골든 fixture를 작성합니다.

- [ ] 룬·스킬 Markdown의 malformed/빈/중복/누락/소수점/OCR 노이즈 회귀 fixture를 추가합니다.

- [ ] `Calculator`의 `localStorage` 로드·마이그레이션·자동 저장·손상 데이터 fallback을 컴포넌트 테스트로 보강합니다.

- [ ] 프리셋과 리셋의 상태 범위(`stats`, 룬, 초월, 보석, 사이클, 가동률, 스탠스, 기믹, 인장)를 제품 책임자와 확정하고 저장·복원·초기화 테스트로 고정합니다.

- [ ] 보석 UI와 계산 유틸리티의 결과 동등성 테스트를 추가하고, 중복 로직 통합 여부를 후속 리팩터링 작업으로 등록합니다.

- [ ] Playwright P0 시나리오를 구현하여 기본 계산, 장착·초월, 보석, 프리셋 새로고침, 모바일 뷰포트, 페이지 오류 0건을 검증합니다.

- [ ] 핵심 계산·파서 유틸리티의 Statements/Branches/Functions/Lines 전역 커버리지 **95%** 임계값을 활성화하고, UI는 별도의 통합·E2E 핵심 시나리오를 100% 통과시킵니다.

**완료 조건:** 데이터 파싱 실패와 브라우저 상태 복원이 빈 화면·잘못된 계산·상태 손실로 이어지지 않으며, P0 E2E가 안정적으로 통과합니다.

### 4.4 4단계 — 품질 관문·보안 검사·배포 연결

- [ ] 선택한 CI/CD 옵션에 따라 PR과 `main` push에서 동일한 verify 파이프라인을 실행하도록 구성합니다.

- [ ] verify 파이프라인에 `npm ci`, format/lint, unit/component tests, coverage, production build, P0 E2E를 순서대로 연결합니다.

- [ ] Semgrep JavaScript SAST, 시크릿 스캔, `npm audit`를 추가합니다. 초기에는 기존 이슈를 보고 모드로 운영하고, 기준선 해결 후 High/Critical 차단 모드로 전환합니다.

- [ ] 커버리지 보고서와 Playwright trace·screenshot을 CI 산출물로 업로드합니다.

- [ ] Pages 배포 작업이 verify 성공에 의존하도록 변경하고, 실패 시 artifact 업로드 및 배포를 막습니다.

- [ ] 브랜치 보호를 사용할 경우 필수 상태 검사를 지정하고, 관리자가 임계값 우회를 허용하는 예외 절차와 만료일을 기록합니다.

- [ ] 월 1회 또는 의존성 변경 PR마다 audit·정적 분석 결과를 검토하는 운영 절차를 문서화합니다.

**완료 조건:** 테스트 실패, 커버리지 저하, 린트 위반, High/Critical 보안 문제, 빌드 실패, P0 E2E 실패 중 하나라도 발생하면 `main` 병합 또는 Pages 배포가 차단됩니다.
